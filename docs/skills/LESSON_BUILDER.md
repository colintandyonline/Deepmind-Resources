# Lesson Builder Skill

This skill defines how DeepMindResources should create, update, structure, and validate learning material.

The Lesson Builder skill turns verified AI intelligence into practical education for beginners, intermediate learners, advanced builders, and business teams.

---

## Core Purpose

The Lesson Builder exists to make AI understandable, practical, and current.

It should turn verified updates, Master Brain records, tool intelligence, and sandbox outcomes into lessons that help users build real skill.

The goal is not to create generic AI course content.

The goal is to create living AI lessons that stay useful as tools, models, APIs, and workflows change.

---

## Product Promise Connection

Every lesson should support the DeepMindResources product loop:

AI update → verified meaning → practical lesson → sandbox task → user skill gain

A lesson is only valuable if it helps the user understand something clearly and apply it practically.

---

## Lesson Types

DeepMindResources may create several lesson types:

- Beginner explanation
- Concept lesson
- Practical workflow lesson
- Tool-specific lesson
- Model comparison lesson
- Prompt engineering lesson
- Agent-building lesson
- Tool-calling lesson
- RAG lesson
- Multi-agent lesson
- Safety and validation lesson
- Business productivity lesson
- Team training lesson
- Update briefing lesson
- Sandbox companion lesson

Each lesson type should have a clear audience and purpose.

---

## Required Lesson Questions

Before creating or updating a lesson, answer:

1. Who is this lesson for?
2. What skill does it teach?
3. What problem does it solve?
4. What should the learner understand by the end?
5. What should the learner be able to do by the end?
6. Is the lesson based on verified information?
7. Which Master Brain records support it?
8. Which tools, models, or platforms are involved?
9. Does it need a sandbox task?
10. Does it need business context?
11. Is the lesson beginner, intermediate, advanced, or business-facing?
12. What previous knowledge is required?
13. What should the learner do next?

## Lesson Structure

A strong lesson should usually include:

- Clear title
- Short summary
- Audience level
- Learning outcome
- Why this matters
- Plain-English explanation
- Practical examples
- Common mistakes
- Step-by-step guidance where useful
- Short recap
- Practice task or sandbox link
- Related lessons
- Source and validation note where relevant

Lessons should be easy to scan, but not shallow.

---

## Learning Levels

Lessons should be tagged by learner level.

### Beginner

For users who are new to AI or the topic.

Beginner lessons should:

- Avoid unexplained jargon
- Use clear examples
- Explain why the concept matters
- Focus on confidence and understanding
- Avoid overwhelming technical detail

### Intermediate

For users already using AI tools.

Intermediate lessons should:

- Teach workflows
- Compare approaches
- Explain trade-offs
- Introduce practical patterns
- Connect concepts to real use cases

### Advanced

For technical builders and power users.

Advanced lessons should:

- Explain architecture
- Include implementation detail
- Discuss limitations
- Connect to APIs, agents, RAG, or automation
- Include debugging and validation thinking

### Business

For teams, managers, and workplace training.

Business lessons should:

- Focus on practical adoption
- Explain staff workflows
- Include tool selection guidance
- Address risk, privacy, cost, and training needs
- Avoid unnecessary technical depth unless relevant

## Lesson Quality Rules

A lesson must be:

- Clear
- Accurate
- Current
- Practical
- Search-intent aligned
- LLM-readable
- Free from unsupported hype
- Connected to the DeepMindResources product promise

Avoid:

- Generic AI filler
- Empty motivational copy
- Outdated tool behaviour
- Unsupported model claims
- Random lists with no teaching value
- Lessons that do not lead to practice

---

## Source and Validation Rules

Lessons should be based on verified knowledge.

Use:

- Master Brain records
- Official documentation
- Official release notes
- Validated tool comparisons
- Reproducible tests
- Trusted technical sources

If a lesson includes time-sensitive claims about models, tools, APIs, pricing, or platform features, it should include a date checked or validation note in the underlying record.

Do not build lessons from weak sources alone.

---

## Update Rules

A lesson should be updated when verified information changes what users need to learn or practise.

Triggers include:

- New model capability
- API syntax change
- Feature deprecation
- Tool workflow change
- Pricing or plan change that affects recommendations
- Safety recommendation change
- Platform behaviour change
- Better validated explanation available

Do not update lessons for every small news item.

Update only when there is practical learning value.

---

## Lesson-to-Sandbox Rule

Lessons should connect to practice whenever possible.

A lesson may link to:

- Prompt test
- Tool-calling exercise
- Agent-building task
- RAG exercise
- Debugging challenge
- Model comparison task
- Business workflow simulation
- Validation challenge

The learner should not only read about AI.

They should practise using it.

---

## SEO and AI Search Rules

Public lessons are search assets.

Every public lesson should include:

- Unique title
- Unique meta description
- One H1
- Clear search intent
- Plain-English summary near the top
- Helpful headings
- Definitions where needed
- Examples and practical steps
- FAQ section where useful
- Related lesson links
- Related sandbox links

AI search systems should be able to understand what the lesson teaches and who it is for.

---

## Business Lesson Rules

Business-facing lessons should focus on workplace outcomes.

They should answer:

- What business problem does this solve?
- Which staff roles does it help?
- What tools are involved?
- What training is required?
- What risks should be managed?
- What measurable workflow improvement is possible?

Avoid promising unrealistic productivity gains.

---

## Common Mistakes Section

Where useful, lessons should include common mistakes.

Examples:

- Using a tool before understanding the use case
- Trusting AI output without validation
- Choosing a model because it is popular, not suitable
- Building agents without clear tool boundaries
- Using RAG without source quality checks
- Automating business workflows without approval or testing

Mistakes should include practical fixes.

---

## Assessment and Progress

Lessons may include assessment prompts such as:

- Quick check questions
- Practical reflection questions
- Mini tasks
- Sandbox completion requirements
- Confidence self-rating
- Business scenario questions

Progress tracking should reflect skill gain, not just reading completion.

---

## Agent Responsibilities

### Lesson Builder Agent

Creates lesson drafts from verified records.

### Validator Agent

Checks lesson accuracy and source grounding.

### Sandbox Builder Agent

Creates practice tasks linked to lessons.

### Tool Agent

Provides tool capability and limitation records.

### Business Training Agent

Adapts lessons for teams and workplace use cases.

### Noise Filter Agent

Prevents hype or weak claims from becoming lessons.

---

## Definition of Done

A lesson is complete when it has:

- Clear audience
- Clear learning outcome
- Accurate explanation
- Verified source basis
- Practical examples
- Common mistakes or caveats where useful
- Related sandbox task where useful
- Related lessons where useful
- SEO metadata if public
- AI-search readable structure
- No unsupported hype

---

## Locked Rule

DeepMindResources lessons must teach current, practical, verified AI skills.

A lesson should never exist just to fill space.
