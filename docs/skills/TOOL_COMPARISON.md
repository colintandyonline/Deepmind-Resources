# Tool Comparison Skill

This skill defines how DeepMindResources should compare AI tools, platforms, coding assistants, automation tools, agent frameworks, and business AI products.

Tool comparisons are a major part of the platform because users and businesses need help choosing the right AI tools for real use cases.

---

## Core Rule

Do not say one AI tool is universally best.

Every tool recommendation must be use-case based, evidence-aware, and clearly matched to the user's needs, skill level, budget, and constraints.

DeepMindResources should help users avoid wasting time and money on tools that do not fit their actual scenario.

---

## Product Promise Connection

Tool comparisons should support the wider DeepMindResources loop:

AI update → verified meaning → practical lesson → sandbox task → user skill gain

A tool comparison is useful when it helps the user understand:

- Which tool fits their task
- Why that tool fits
- What trade-offs exist
- What skill they need to use it well
- Whether a lesson or sandbox task can help them practise

## Use-Case First Comparison

Always compare tools by use case.

Examples:

- Best AI tool for coding
- Best AI tool for research
- Best AI tool for business automation
- Best AI tool for customer service
- Best AI tool for writing
- Best AI tool for data analysis
- Best AI tool for building agents
- Best AI tool for internal company knowledge
- Best AI tool for non-technical staff
- Best AI tool for prompt engineering practice
- Best AI tool for RAG workflows
- Best AI tool for small businesses
- Best AI tool for teams

Avoid vague comparisons such as:

- Best AI tool overall
- Top AI tools ranked
- Best chatbot
- Best AI app

Those are usually too broad to be useful.

---

## Required Comparison Questions

Every useful tool comparison should answer:

1. What is the user trying to do?
2. Is the user technical or non-technical?
3. Is this for an individual, team, or business?
4. What skill level is required?
5. Which tools are being compared?
6. What evidence supports the comparison?
7. What are each tool's strengths?
8. What are each tool's limitations?
9. What are the cost or plan considerations?
10. What integrations matter?
11. What privacy, data, or security concerns matter?
12. Which tool is best for this exact scenario?
13. Which tool should the user avoid for this scenario?
14. What lesson or sandbox task should help the user practise?

---

## Evidence Requirements

Tool comparisons should be based on evidence.

Preferred evidence:

- Official documentation
- Official pricing pages
- Official release notes
- Official feature pages
- Direct product testing
- API tests
- Reproducible workflow tests
- Trusted technical reviews
- Multiple-source agreement

Avoid basing comparisons only on:

- Affiliate articles
- Social media hype
- Sponsored rankings
- Marketing copy
- Old tutorials
- Unsourced claims
- Personal preference with no scenario

---

## Comparison Dimensions

When comparing tools, consider the dimensions that matter for the use case.

Possible dimensions:

- Core capability
- Output quality
- Reliability
- Speed
- Context window or memory behaviour
- Tool-calling support
- Agent workflow support
- Coding ability
- Research quality
- Citation quality
- Data analysis capability
- Automation integrations
- RAG support
- Team/admin features
- Security and privacy
- Ease of use
- Learning curve
- Pricing and plan limits
- API availability
- Documentation quality
- Community and ecosystem
- Enterprise readiness
- Non-technical staff suitability

Do not use every dimension on every page.

Choose the dimensions that fit the scenario.

## Recommended Output Format

A good tool comparison should usually include:

- Short answer summary
- Best tool by scenario
- Comparison table
- Strengths and weaknesses
- Practical examples
- Who should use each tool
- Who should avoid each tool
- Pricing or plan caveats
- Trust and validation notes
- Related lessons
- Related sandbox tasks
- FAQ section where useful

For search and AI readability, the page should make the recommendation clear near the top, then explain the reasoning below.

---

## Ranking Rules

Avoid shallow rankings.

Do not rank tools only because they are popular.

A ranking is valid only when:

- The scenario is clear
- The evaluation criteria are clear
- The evidence is stated
- Trade-offs are explained
- The recommendation is current enough to be useful

Good ranking language:

- Best for non-technical business teams
- Best for developer workflows
- Best for fast research with citations
- Best for visual workflow automation
- Best for agent framework experimentation

Bad ranking language:

- Best AI tool overall
- Number one AI platform
- Ultimate winner
- Beats every other AI tool
- The only AI tool you need

---

## Pricing and Plan Caution

Pricing changes often.

When discussing pricing:

- Prefer official pricing pages.
- Store the date checked.
- Avoid exact claims unless recently verified.
- Mention plan limitations when relevant.
- Be careful with free, pro, team, business, and enterprise differences.

Do not recommend a tool for a business without checking whether the required features are available on the right plan.

---

## Business Comparison Rules

Business recommendations require extra caution.

For business use cases, compare:

- Team management
- Admin controls
- Security posture
- Data privacy
- Compliance needs
- Integrations
- Staff skill level
- Training requirements
- Total cost of ownership
- Vendor maturity
- Support options
- Workflow fit

Avoid telling businesses to adopt tools based only on novelty or popularity.

---

## Technical Builder Comparison Rules

For developers and technical builders, compare:

- API quality
- SDK support
- Documentation
- Model capability
- Function/tool-calling behaviour
- Latency
- Rate limits
- Cost per usage pattern
- Framework compatibility
- Observability and debugging
- Deployment fit
- RAG and agent workflow support

Technical comparisons should be precise and should avoid vague claims.

---

## Non-Technical User Comparison Rules

For non-technical users, compare:

- Ease of use
- Setup time
- Template support
- Workflow clarity
- Risk of mistakes
- Learning curve
- Support and documentation
- Whether the tool requires coding
- Whether the tool can be used safely by staff

Do not recommend complex tools to non-technical users unless the page explains the training or support required.

## Tool Capability Records

When a comparison affects the Master Brain, record:

- Tool name
- Capability
- Limitation
- Use case
- Source reference
- Date checked
- Confidence score
- Pricing or plan dependency
- Related lesson
- Related sandbox task
- Comparison pages affected

Capabilities should be specific.

Bad capability record:

- Good for business

Good capability record:

- Supports visual workflow automation for common SaaS apps, suitable for non-technical operations teams when prebuilt integrations cover the required workflow.

---

## Conflict Handling

If sources disagree, do not hide the conflict.

Use wording such as:

- Official documentation says...
- Our test found...
- Some third-party reviews claim..., but this is not yet confirmed by official sources.
- Evidence is currently mixed.

Conflicting claims should be marked for review in the Master Brain.

---

## Tool Deprecation and Change Rules

When a tool changes significantly, comparison pages may need updates.

Triggers include:

- Feature launch
- Feature removal
- Pricing change
- API change
- Model upgrade
- Model downgrade
- Tool deprecation
- Security or privacy change
- Major integration change
- Major reliability issue

These should create Live AI Intelligence items and Master Brain update records.

---

## Related Lesson Rules

Tool comparisons should connect to training.

Examples:

- A coding assistant comparison should link to AI coding lessons.
- A research tool comparison should link to research workflow lessons.
- A business automation comparison should link to automation training.
- An agent framework comparison should link to agentic workflow lessons.

The goal is not just to recommend tools, but to help users build the skill to use them well.

---

## Related Sandbox Rules

Where possible, tool comparisons should create or link to sandbox tasks.

Examples:

- Compare two models on the same prompt.
- Build the same workflow in n8n and Zapier.
- Test a coding assistant on a debugging task.
- Compare research outputs with citation quality.
- Build a simple agent using two frameworks.

This helps users learn through practical evidence instead of trusting a ranking blindly.

---

## SEO and AI Search Rules

Tool comparison pages are important search assets.

Each comparison page should include:

- Clear search intent
- Unique title
- Unique meta description
- One H1
- Practical summary near the top
- Scenario-based recommendation
- Comparison table
- Evidence and caveats
- FAQ section where useful
- Internal links to lessons and sandbox tasks

The page should be easy for AI search systems to summarise accurately.

## Definition of Done

A tool comparison is complete when it has:

- Clear use case
- Defined audience
- Tools compared
- Evidence sources
- Strengths and limitations
- Pricing or plan caveats
- Recommendation by scenario
- Confidence level
- Related lessons where useful
- Related sandbox tasks where useful
- SEO metadata
- AI-search readable structure
- No unsupported hype claims
